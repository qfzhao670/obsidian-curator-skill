# 功能④：把一次已解决的对话总结成博客笔记

当用户**明确要求**把「本次对话」总结抽象成一篇博客风格的 Obsidian 笔记时
（例如说「当前的内容可以总结成一篇 obsidian 笔记，请总结」），遵循本文件。
输入是**当前对话的上下文**；输出是写给陌生读者的 CSDN 风格技术博客，落到用户指定的 Obsidian 目录。

**范围不限于 debug**：本次对话既可以是「解决了一个 bug / 实现了一个需求」的开发调试过程，
也可以是「回答了一个技术知识点 / 概念问题」的知识问答过程。两类都能成文，只是输出结构略有不同（见「输出结构」）。

## 第一步：先判断能不能成文、成几篇、要不要新建

动笔前，先对整段上下文做一次「规划」，回答三个问题：

1. **能不能成文**：本次对话是否有一个**完整、已解决 / 已讲清**的结论？
   - 若问题还没解决、结论还不确定，**不要**强行成文，先向用户说明「这个对话还不能总结成一篇完整的帖子」。

2. **成几篇**：这段对话是在解决**同一个问题**，还是夹杂了多个**互不相干**的问题？
   - 判断标准：是否围绕同一个 bug / 同一个知识点。若对话中途转向了另一个完全不同的 bug 或知识点，
     应**拆成多篇笔记**，每篇只讲一个主题，不要硬塞进一篇。
   - 一时拿不准是否算「同一个问题」时，倾向拆分，并向用户说明你打算拆成哪几篇、各自标题是什么，请用户确认。

3. **要不要新建**：当前这个 bug / 知识点，是否和目标目录里**已有的某篇笔记非常相似**？
   - 先到用户指定的目标目录（必要时扩大到整个 vault）搜索，看有没有主题相近的笔记。
   - 若发现高度相似的已有笔记，**先询问用户**：是「把新内容补充进原有笔记」，还是「新建一篇」；
     在用户确认前，不要覆盖、合并或重复建篇。

## 核心原则（优先级最高）

1. **忠实于对话**：只写这次对话里真实发生的问题、排查过程与最终方案，不编造、不夸大、不添油加醋。
2. **抽象通用化**（本功能的核心价值）：把「我这个项目、这台机器上的具体 bug」抽象成「这类问题的通用解法」。
   - 去掉：真实项目名、公司名、人名、内网 IP / 域名、真实路径、账号 / 密钥 / token 等敏感信息。
   - 保留：技术要点、报错关键信息、可复现的排查与解决步骤。
   - 代码 / 命令示例里的具体值用占位名代替（如 `your-project`、`your-service`、`your-branch`）。
3. **博客视角**：读者是**遇到同类问题的陌生人**，不是项目协作者。必须交代背景、环境、报错、完整步骤，
   让他们照着就能复现、就能解决；项目内部才知道的上下文要补成读者能看懂的说法。

## 输出结构

### 开发 / debug 类

| 小节 | 内容 |
| --- | --- |
| frontmatter | `tags`、`aliases`、`source`（可写「开发记录」）、`date` |
| 标题 `#` | 一句话概括问题，如「解决 xxx 报错」或「xxx 踩坑记录」 |
| 前言 | 一两句背景：在做什么事、遇到了什么问题 |
| 问题描述 | 现象、报错信息、触发条件（贴关键报错原文） |
| 排查过程 | 怎么定位的：先尝试了哪些、排除了哪些、最终如何锁定 |
| 根因分析 | 为什么会出现这个问题（讲清机理，而不是只给结论） |
| 解决方案 | 可复现的步骤 / 命令 / 代码块（只写用户采用的那种，见下一节） |
| 总结 / 踩坑点 | 提炼通用经验（callout，≤2 个）；可选「参考链接」（只放官方文档） |

### 知识问答类

| 小节 | 内容 |
| --- | --- |
| frontmatter | `tags`、`aliases`、`source`（可写「知识问答」）、`date` |
| 标题 `#` | 一句话点出问题，如「xxx 到底是什么 / 为什么需要 xxx」 |
| 问题 / 背景 | 这个知识点是在什么场景下被问起的，想解决什么困惑 |
| 核心结论 | 先直接给出答案（一句话 / 一小段），再往下展开 |
| 详细解释 | 讲清原理、机制、与易混概念的区别，可配合代码 / 命令示例 |
| 常见误区 / 延伸 | 容易理解错的地方，或相关的进阶点 |
| 总结 | 用 callout 收束要点（≤2 个）；可选「参考链接」（只放官方文档） |

## 解决方案：只写用户采用的那种（debug 类）

- 若对话里讨论过多个候选方案（如「方案一 / 方案二」，或先后试了几种），**只写用户最终采用、验证通过的那一种**，
  不要罗列成「方案一、方案二」让读者自己挑。
- 如果**不清楚用户最终用的是哪一种**，先询问用户「最终采用的是哪个方案」，确认后再写，不要猜。

## 格式规则

- 复用 `references/formatting-guide.md`：frontmatter、tags、callout、外链、表格的写法与克制原则。
- **代码块**：贴完整的报错与修复代码，用 ``` 围栏并标注语言；报错原文不要截断关键信息。
- 标题层级克制（`#` + `##`，最多 `###`）。
- 外链只加公认官方文档，拿不准的不加。

## 写回

1. 目标目录由用户指定（如「写到 xxx 目录」）；**用户未给路径时，先向用户确认 vault 路径与目标目录**，不要猜。
2. 默认**生成新文件**，文件名用文章标题（如 `解决 MySQL 连接超时.md`）。
   - 若按「第一步」判断要拆成多篇，则一次生成多篇，各篇标题对应一个主题。
   - 若用户选择「补充原有笔记」，则改为**编辑已有文件**，并在改动前先说明 / 展示将如何修改。
